# CLAUDE.md

Guidance for Claude Code in this repo.

## What This Is

Android + Wear OS companion app for [apollo-server-dashboard](https://github.com/JulioMoralesB/apollo-server-dashboard). Pure client — no functionality without a running dashboard backend. Primary use case: pin individual dashboard actions as home-screen widgets / Wear tiles, not just a mini dashboard.

## Commands

```bash
./gradlew build              # full build
./gradlew :app:assembleDebug # phone app debug APK
./gradlew clean assembleDebug --console=plain 2>&1 | tail -60   # verify after changes
```

Real hardware (a Samsung phone and a Samsung Galaxy Watch) stays connected over adb-over-network whenever Android Studio is running, even in a session whose shell doesn't have `adb` on `PATH` — check `~/Library/Android/sdk/platform-tools/adb devices -l` directly before assuming there's no device to verify against. When it's there, install and drive it for real (logcat, screencap, input, dumpsys) rather than trusting a green build alone — this project has hit real bugs (round-screen clipping, lost `BasicTextField` state, a Data Layer package-id mismatch, a Tile `exported` flag, widgets that silently couldn't resize) that only showed up on-device. Only fall back to "a successful `assembleDebug` is the verification bar" if `adb devices` actually comes back empty.

## Modules

- `core/` — shared networking (Retrofit/OkHttp), auth (JWT access/refresh via `TokenAuthenticator`, transparent silent refresh), `EncryptedSharedPreferences` storage (`TokenStore`, `ServerConfigStore`, `CloudflareAccessStore`). `retrofit-core` is exposed as `api` (not `implementation`) so callers can catch `HttpException`. Also owns the summary feature's shared model/parsing (`model/SummaryModels.kt`, `SummaryFormat.kt`) — see Key Conventions.
- `app/` — phone app: login, dashboard (`ui/dashboard/`), settings, home-screen widgets (`widget/`). Dashboard mirrors the web's summary panel: a service with a `summary_endpoint` shows its parsed `ServiceSummary` inside its own panel, above the action grid. Configure UI is Compose; widgets render via plain `RemoteViews`/`AppWidgetProvider` (`WidgetRemoteViews.kt` etc.), not Jetpack Glance — Glance's session/recomposition layer proved unreliable for background-triggered updates (tap feedback, WorkManager-driven revert) on-device. Three widget types: the original single-action widget (`ActionWidget.kt`), a per-service summary widget (`SummaryWidget.kt`, condensed to ≤3 lines via `condensedSummaryLines()`), and a combined summary widget (`CombinedSummaryWidget.kt`, no config — one row per service that has a summary) — see below.
  - Summary widgets (`app/.../widget/Summary*.kt`, `CombinedSummaryWidget*.kt`): same render-from-cache discipline as the Wear tiles below — `SummaryRefreshWorker` is the only thing that touches the network (a 15-min periodic `WorkManager` job, scheduled while any summary widget is placed and cancelled once none remain, plus a one-time immediate run right after placement/reconfigure), caching raw JSON per service in `SummaryWidgetCache` for both widgets' `RemoteViews` builders to read synchronously. Tapping a row opens `MainActivity` with `EXTRA_OPEN_SERVICE_NAME` — `MainActivity` is `launchMode="singleTop"` + overrides `onNewIntent` so this deep-links correctly whether the app is already running or not. Two hardware-confirmed gotchas: an omitted `minResizeWidth`/`minResizeHeight` silently defaults to `minWidth`/`minHeight`, blocking resize-smaller even with room to spare (both now set explicitly); and a `<receiver>` with no `android:label` falls back to the app's own name in the system widget picker — with three receivers that meant three identical "Apollo Deck" entries, distinguishable only by size preview.
- `wear/` — Wear OS app (`standalone=true`, no phone pairing required, but the login screen's primary path uses one when available — see below). Has its own login (`presentation/login/`, reuses core's `AuthRepository`/`ApiClient`) and an actions list (`presentation/actions/`) that fetches `/services` and executes actions — no `TextField` in Wear Compose Material, so input fields are hand-rolled from `BasicTextField`; `confirm: true` actions require a long-press instead of a dialog. Its own `IconMapping` (`wear/.../icons/IconMapping.kt`) duplicates the phone app's Lucide→Material dictionary (`app/.../ui/icons/IconMapping.kt`) — not shared via `core/`, which deliberately has no Android UI deps.
  - Tiles (`wear/.../tile/`): `ActionTileService` (one pinned action, big circular tap-to-run button) and `MultiActionTileService` (icon-only grid, phone-configured — see below). Module is `compileSdk = 35` (AGP 8.6.1) since `androidx.wear.tiles:tiles:1.6.0` requires it. A Tile's `Clickable` can only launch an Activity or fire a `LoadAction` (re-request the tile) — no PendingIntent-to-broadcast like RemoteViews — so running an action means: `Clickable` sets a `LoadAction`, `onTileRequest` reads the click via `requestParams.currentState.lastClickableId`, and fires `TileActionReceiver` (execute + status + `WorkManager` revert, mirrors the widget's `ActionWidgetReceiver`/`RevertWidgetStatusWorker`) before rendering. `TileConfigActivity` (launched via `LaunchAction` from "Tap to configure") **must be `exported="true"`** — confirmed on hardware: the renderer firing `LaunchAction` runs in a different process/UID (`com.samsung.android.wearable.sysui`), and logs `Activity constraints not met` otherwise.
  - **`TileActionReceiver` must not bind a service (`TileService.getUpdater(...).requestUpdate(...)` included) using the `Context` `onReceive` was handed** — even from a `goAsync()`-extended coroutine, that `Context` still throws `ReceiverCallNotAllowedException`, crashing the app. This was the real cause of a tile appearing permanently "stuck" on its last result: the crash landed after the status write but before `scheduleTileStatusRevert`, on every execute — not WorkManager deferral, as first suspected. Fix: capture `context.applicationContext` at the top of `onReceive`, use that throughout.
  - **`onTileRequest`/`onTileResourcesRequest` must never do network or Data Layer I/O directly** — confirmed repeatedly on hardware: the system cancels a slow response (`Future failed`/`JobCancellationException`) well before an 8s+ timeout, and a cold process alone can burn most of that budget. Both tile services render from local `SharedPreferences` only, with network/Data Layer work in a decoupled `WorkManager` job that calls `requestUpdate()` when done — a coroutine on the `TileService`'s own scope isn't decoupled enough, since the system tears the service down (cancelling its scope) seconds after a single request.
  - Tile icons are rasterized Material icons baked into inline `protolayout` image resources (`TileImageResources.kt`) — no live Compose tree to draw into, so an `ImageVector` is rendered to a `Bitmap` by hand (mirrors the phone widget's `IconRasterizer`) and copied in as raw `IMAGE_FORMAT_ARGB_8888` bytes, not PNG. **`resourcesVersion` must change whenever the icon does** — the renderer only re-fetches resources when that string differs from its cache, so both tile services derive it from actual icon/action state (`resourcesVersionFor`).
  - `ActionTileService` can be pinned more than once, keyed by its numeric `tileId` (same shape as the widget's per-`appWidgetId` config — `TileActionConfig.kt`, also carrying `iconName`/`accentColor`). A Tile has no per-instance configure extras, so `tileId` rides along as a `LaunchAction` `AndroidActivity` intent extra to `TileConfigActivity`. Its circular tap target is hand-built (`Box`/`Image`/`Modifiers`) rather than `protolayout-material`'s `Button`, which always fills its background with no opt-out — this design needed icon + thin accent ring, no fill.
  - `MultiActionTileService` renders a grid of icon-only circular buttons (`protolayout.material.Button`), styled after Home Assistant's Wear shortcuts / the watch's own launcher grid. Which actions appear and in what order is **configured from the phone**, not the watch (see below). Like the widget and `ActionTileService`, nothing here is fire-and-forget: since a Tile's `Clickable` can't distinguish long-press from tap, a `confirm: true` action needs a first tap to arm (`TileColors.warning`, `TileGridArmState.kt`) and a second tap on the same icon within `GRID_ARM_TIMEOUT_MS` to run. Whichever icon most recently completed a run flashes success/error for `GRID_STATUS_HOLD_MS` (`TileGridActionStatus.kt`, reported via `TileActionReceiver`'s `EXTRA_TRACK_GRID_INDEX`, separate from `ActionTileService`'s `EXTRA_TRACK_STATUS_TILE_ID` — different stores). Both arm and result states self-clear on read past their window, plus a `setFreshnessIntervalMillis` nudge.
- Phone → watch session sync (`app/.../wearsync/`, `wear/.../sync/`): the watch's login leads with "Sign In from Phone" rather than typing credentials — the phone publishes its session as a synced Wear Data Layer `DataItem` (`PhoneSessionPublisher`, on login/logout/app-open), the watch reads whatever's synced (`PhoneSessionSync`, a `DataClient.getDataItems()` pull, not live). `core/.../sync/SessionTransfer.kt` is the wire format. Manual entry stays as a fallback.
- Phone → watch grid-tile config (`TileGridConfigScreen.kt`/`TileGridPublisher`, `wear/.../tile/{TileGridSync,TileActionsCache,GridTileRefreshWorker,TileGridDataListenerService}.kt`): same synced-`DataItem` approach, since picking actions out of a long list is as painful on a watch as typing credentials. Settings → "Configure watch tile" is a checklist grouped by service; tap order becomes display order, capped at `MAX_TILE_GRID_ACTIONS` (9). Saves a list of `serviceName`+`endpoint` refs (`TileGridSelection.kt`), not label/icon/confirm.
  - `MultiActionTileService`'s render (`resolveDisplayedActionsFast`) reads only two local caches — `TileActionsCache` and `TileGridSync`'s selection — never network/`DataClient` directly. `TileGridDataListenerService` (a `WearableListenerService` scoped to `/apollo-deck/tile-grid`) updates the selection cache and calls `requestUpdate()` on push; `GridTileRefreshWorker` (enqueued per render, debounced to ~once/minute) refetches the action list and does a catch-up `DataClient` pull as backstop. Falls back to the first few cached actions if nothing's ever synced.
  - **`wear/`'s `applicationId` must exactly match `app/`'s** (`com.apollox10.apollodeck`) — Wear Data Layer only routes `DataClient`/`MessageClient` traffic between apps it can verify are "the same app" (package + signing cert); `namespace` can differ, only `applicationId` matters. Confirmed on hardware: a mismatch failed `MessageClient` delivery and left `DataClient.getDataItems()` empty on the watch minutes after a confirmed phone-side `putDataItem`; both started working the moment the ids matched.
- Icon overrides (`IconOverrideStore.kt`, `IconOverrideSync.kt`, `IconOverride{Screen,ViewModel}.kt`, `wear/.../tile/{IconOverrideSync,IconOverrideDataListenerService}.kt`): `iconFor()`'s dictionary inevitably misses a name (e.g. `lucide-file-plus`) — Settings → "Icon overrides" lets you point any backend icon name at a Material icon (same namespace as the widget picker, `availableIcons`/`widgetIconFor`), stored in plain `SharedPreferences` and synced to the watch. Every icon call site uses `resolvedIconFor(context, name)`, which checks the override first. Both tile services fold the resolved override into `resourcesVersionFor` — otherwise a changed override wouldn't force a re-render.

## Key Conventions

- Kotlin 2.0 Compose: apply `org.jetbrains.kotlin.plugin.compose` in every module with `buildFeatures.compose = true`.
- `kotlinx.serialization`: needs both the Gradle plugin per-module AND explicit imports `kotlinx.serialization.encodeToString`/`decodeFromString` (the reified extensions, not the base `Json` members).
- Lucide icon names (from the dashboard's `services.yaml`) have no Compose port — mapped manually to Material Icons Extended in `app/.../ui/icons/IconMapping.kt` and duplicated in `wear/.../icons/IconMapping.kt`. New service icons need an entry in both — or don't, since a wrong/missing mapping is now also fixable from inside the app (see icon overrides, above). Any icon-rendering call site should use `resolvedIconFor(context, name)`, not `iconFor(name)` directly, so it honors an override.
- Widgets/tiles reuse the phone app's stored session (no separate login) and must tolerate silent background token refresh — no interactive re-auth possible.
- Widget config/status live in plain `SharedPreferences` (`apollo_deck_widgets`, keyed by `appWidgetId`; the summary widgets use their own `SummaryWidgetCache`/`SummaryWidgetConfig`), not DataStore — reads must work synchronously from `BroadcastReceiver.onReceive` and from a `CoroutineWorker`. A placed widget supports long-press → reconfigure (`widgetFeatures="reconfigurable"`).
- Match the web dashboard's action model: `method: "href"` = external link (skip in anything that "executes" an action), `confirm: true` = should get a visual warning where no confirm dialog is possible (e.g. widgets).
- Summary feature: a service's `summary_endpoint` is fetched and parsed into `ServiceSummary` (`core/.../model/SummaryModels.kt`) by dispatching on response shape, not service name — mirrors the web dashboard's `SummaryPanel.jsx`, including `SummaryFormat.kt`'s `formatEta` comparing dates by local calendar day (not raw elapsed hours, which misreads a date as "today" for viewers behind UTC). The dashboard panel and both summary widgets all share this same parsing/formatting code.

## Workflow

Always use PRs — never push to `main` directly. Verify Kotlin/Gradle changes with a real `./gradlew` build before calling work done, not just code review.

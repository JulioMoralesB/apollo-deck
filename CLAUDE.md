# CLAUDE.md

Guidance for Claude Code in this repo.

## What This Is

Android + Wear OS companion app for [apollo-server-dashboard](https://github.com/JulioMoralesB/apollo-server-dashboard). Pure client — no functionality without a running dashboard backend. Primary use case: pin individual dashboard actions as home-screen widgets / Wear tiles, not just a mini dashboard.

## Commands

```bash
./gradlew build              # full build
./gradlew :app:assembleDebug # phone app debug APK
./gradlew clean assembleDebug --console=plain 2>&1 | tail -60   # verify after changes
```

Real hardware (a Samsung phone and a Samsung Galaxy Watch) stays connected over adb-over-network whenever Android Studio is running, even in a session whose shell doesn't have `adb` on `PATH` — check `~/Library/Android/sdk/platform-tools/adb devices -l` directly before assuming there's no device to verify against. When it's there, install and drive it for real (logcat, screencap, input, dumpsys) rather than trusting a green build alone — this project has hit real bugs (round-screen clipping, lost `BasicTextField` state, a Data Layer package-id mismatch, a Tile `exported` flag) that only showed up on-device. Only fall back to "a successful `assembleDebug` is the verification bar" if `adb devices` actually comes back empty.

## Modules

- `core/` — shared networking (Retrofit/OkHttp), auth (JWT access/refresh via `TokenAuthenticator`, transparent silent refresh), `EncryptedSharedPreferences` storage (`TokenStore`, `ServerConfigStore`, `CloudflareAccessStore`). `retrofit-core` is exposed as `api` (not `implementation`) so callers can catch `HttpException`.
- `app/` — phone app: login, dashboard (`ui/dashboard/`), settings, home-screen widget (`widget/`). Configure UI is Compose (`WidgetSetupScreen.kt`); the widget itself renders via plain `RemoteViews`/`AppWidgetProvider` built directly in `WidgetRemoteViews.kt`, not Jetpack Glance — Glance's session/recomposition layer was found unreliable for background-triggered updates (tap feedback, WorkManager-driven revert) on-device, so it was dropped in favor of pushing `RemoteViews` straight to `AppWidgetManager`.
- `wear/` — Wear OS app (`standalone=true`, no phone pairing required, but the login screen's primary path uses one when available — see below). Has its own login (`presentation/login/`, reuses core's `AuthRepository`/`ApiClient`) and an actions list (`presentation/actions/`) that fetches `/services` and executes actions — no `TextField` in Wear Compose Material, so input fields are hand-rolled from `BasicTextField`; `confirm: true` actions require a long-press instead of a dialog. Its own `IconMapping` (`wear/.../icons/IconMapping.kt`) duplicates the phone app's Lucide→Material dictionary (`app/.../ui/icons/IconMapping.kt`) — not shared via `core/`, which deliberately has no Android UI deps.
  - Tiles (`wear/.../tile/`): `ActionTileService` (one pinned action, a big circular tap-to-run button — mirrors the phone widget) and `MultiActionTileService` (a grid of icon-only buttons, phone-configured — see below). This module is `compileSdk = 35` — one higher than `app`/`core` — because `androidx.wear.tiles:tiles:1.6.0` requires it (needed AGP bumped to 8.6.1 too). A Tile's `Clickable` can only launch an Activity or fire a `LoadAction` (re-request the tile) — there's no PendingIntent-to-arbitrary-broadcast the way RemoteViews has — so "run the action" is: `Clickable` sets a `LoadAction`, `onTileRequest` reads the click back via `requestParams.currentState.lastClickableId`, and fires `TileActionReceiver` itself (execute + status + `WorkManager` revert, same shape as the widget's `ActionWidgetReceiver`/`RevertWidgetStatusWorker`) before rendering. `TileConfigActivity` (launched via `LaunchAction` from the unconfigured "Tap to configure" state) **must be `exported="true"`** — confirmed on real hardware: the tile renderer that fires the `LaunchAction` runs in a different process/UID (`com.samsung.android.wearable.sysui` on this device), and logs `Activity constraints not met. Not launching LaunchAction Activity` if it isn't.
  - **A Tile's `onTileRequest`/`onTileResourcesRequest` must never do network or Data Layer I/O directly** — confirmed on real hardware, repeatedly: the system cancels a slow response (`onTileRequest Future failed` / `JobCancellationException` in logcat, `ProtoTilesTileRendererImpl: Error getting tile response` on the renderer side) well before an 8s+ network timeout would ever fire, and a cold app process alone can burn most of that budget before any of the render code even runs. `MultiActionTileService` learned this the hard way (see below) — both tile services now render from local `SharedPreferences` state only, with all network/Data Layer work happening in a decoupled `WorkManager` job that calls `TileService.getUpdater(context).requestUpdate(...)` when it's done. A coroutine merely launched on the `TileService`'s own `CoroutineScope` is **not** decoupled enough — that scope's job gets cancelled when the system tears down the service instance (which it does routinely, seconds after a single request), killing an in-flight "background" fetch too; only genuinely independent work (a `WorkManager` job, a `WearableListenerService`) survives that.
  - Tile icons are rasterized Material icons baked into inline `protolayout` image resources (`wear/.../tile/TileImageResources.kt`) — a Tile's `LayoutElement` can only reference an image by resource id declared in `onTileResourcesRequest`, there's no live Compose tree to draw an `Icon()` into, so an `ImageVector` is walked and rendered to a `Bitmap` by hand (mirrors the phone widget's `IconRasterizer`), then copied into an `InlineImageResource` as raw `IMAGE_FORMAT_ARGB_8888` pixel bytes (not PNG-encoded — that's the format the renderer expects for a runtime-generated bitmap). **`resourcesVersion` must change whenever the underlying icon(s) do** — the renderer only calls `onTileResourcesRequest` again when that string differs from what it already has cached for the tile, so a hardcoded constant would let it keep serving a stale bitmap after a reconfigure; both tile services derive it from the actual icon/action state instead (see `resourcesVersionFor` in each).
  - `ActionTileService` can be pinned more than once — each instance is keyed by its own numeric `tileId` (`TileRequest#getTileId()` / `ResourcesRequest#getTileId()`, available since tiles 1.6.0), the same shape as the phone widget's per-`appWidgetId` config (see `TileActionConfig.kt`, which also carries `iconName` and `accentColor`). A Tile has no per-instance configure-Activity extras of its own, so `tileId` rides along as a `LaunchAction` `AndroidActivity` intent extra (`addKeyToExtraMapping` + `AndroidIntExtra`) from `ActionTileService` to `TileConfigActivity`, which reads it back and saves/reverts against that specific instance. Its circular tap target is hand-built from `Box`/`Image`/`Modifiers` (`ModifiersBuilders.Border`/`Background`, `LayoutElementBuilders.ColorFilter` for icon tint) rather than the `protolayout-material` `Button` component — `Button` always fills its background from `ButtonColors` with no way to opt out, but the design here (icon + a thin ring in the configured accent color, no fill) needed that.
  - `MultiActionTileService` renders a grid of icon-only circular buttons (`androidx.wear.protolayout.material.Button`, `DEFAULT_SIZE`), styled after Home Assistant's Wear shortcuts tile / the watch's own app-launcher grid — no per-action label, no confirm step, tap fires immediately and isn't tracked (no single result slot to show it in). Which actions appear and in what order is **configured from the phone app**, not the watch — see below.
- Phone → watch session sync (`app/.../wearsync/`, `wear/.../sync/`): typing server URL + username + password on a watch keyboard is painful, so the watch's login screen leads with "Sign In from Phone" — the phone publishes its session as a synced Wear Data Layer `DataItem` (`PhoneSessionPublisher`, on login/logout/app-open) and the watch reads whatever's currently synced (`PhoneSessionSync`, a `DataClient.getDataItems()` pull, not a live round-trip). `core/.../sync/SessionTransfer.kt` is the shared wire format (server URL, tokens, optional Cloudflare Access creds) and the `DataItem` path. Manual entry on the watch stays as a fallback for a watch used without a phone nearby.
- Phone → watch grid-tile config (`app/.../wearsync/TileGridConfigScreen.kt` + `TileGridPublisher`, `wear/.../tile/{TileGridSync,TileActionsCache,GridTileRefreshWorker,TileGridDataListenerService}.kt`): the same synced-`DataItem` approach as session sync, reused because picking several actions out of a long list is exactly as painful on a watch as typing credentials is. The phone screen (reachable from Settings → "Configure watch tile") is a checklist grouped by service; tap order becomes display order (shown as a numbered badge), capped at `MAX_TILE_GRID_ACTIONS` (9, mirrored on both sides). Saving writes `core/.../sync/TileGridSelection.kt` (a list of `serviceName`+`endpoint` refs, **not** a full snapshot of label/icon/confirm) to a synced `DataItem`.
  - `MultiActionTileService`'s render path (`resolveDisplayedActionsFast`) reads only two local caches — `TileActionsCache` (the flat action list, from the live `/services` fetch) and `TileGridSync`'s cached selection — never a network call or `DataClient` read directly (see the render-path rule above). Both caches are kept warm out-of-band: `TileGridDataListenerService` (a `WearableListenerService`, manifest-registered against the `DATA_CHANGED` action scoped to the `/apollo-deck/tile-grid` path) updates the selection cache and calls `requestUpdate()` the moment the phone publishes a new one — the system can start it even if the app isn't running; `GridTileRefreshWorker` (`WorkManager`, enqueued from every tile render but debounced to roughly once a minute via a timestamp in `SharedPreferences` — otherwise render → enqueue refresh → `requestUpdate()` → render loops forever) refetches the live action list and does a catch-up `DataClient` pull for the selection, as a bootstrap/backstop for whatever the listener might have missed. With nothing ever synced, the render falls back to the first few cached actions.
  - **`wear/`'s `applicationId` must exactly match `app/`'s (`com.apollox10.apollodeck`)** — Play Services' Wear Data Layer only routes `DataClient`/`MessageClient` traffic between a phone app and watch app it can verify are "the same app" (matching package name + matching signing certificate); a mismatched id makes every call between them silently fail. `namespace` can still differ (it only names the generated R/BuildConfig package) — only `applicationId` needs to match. Confirmed against real paired hardware: a `MessageClient` RPC attempt failed first (`Failed to deliver message to AppKey` in the phone's logcat) and `DataClient.getDataItems()` on the watch came back empty even minutes after a confirmed-successful `putDataItem` on the phone, both while the ids didn't match; both started working immediately once they did.

## Key Conventions

- Kotlin 2.0 Compose: apply `org.jetbrains.kotlin.plugin.compose` in every module with `buildFeatures.compose = true`.
- `kotlinx.serialization`: needs both the Gradle plugin per-module AND explicit imports `kotlinx.serialization.encodeToString`/`decodeFromString` (the reified extensions, not the base `Json` members).
- Lucide icon names (from the dashboard's `services.yaml`) have no Compose port — mapped manually to Material Icons Extended in `app/.../ui/icons/IconMapping.kt` and duplicated in `wear/.../icons/IconMapping.kt`. New service icons need an entry in both.
- Widgets/tiles reuse the phone app's stored session (no separate login) and must tolerate silent background token refresh — no interactive re-auth possible.
- Widget config/status live in plain `SharedPreferences` (`apollo_deck_widgets`, keyed by `appWidgetId`), not DataStore — reads must work synchronously from `BroadcastReceiver.onReceive` and from a `CoroutineWorker`. A placed widget supports long-press → reconfigure (`widgetFeatures="reconfigurable"`).
- Match the web dashboard's action model: `method: "href"` = external link (skip in anything that "executes" an action), `confirm: true` = should get a visual warning where no confirm dialog is possible (e.g. widgets).

## Workflow

Always use PRs — never push to `main` directly. Verify Kotlin/Gradle changes with a real `./gradlew` build before calling work done, not just code review.
